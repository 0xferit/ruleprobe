## Test only when test buys information
A test is worth writing only if it does at least one: explores input space beyond review (fuzz/property tests), pins a singular boundary (0, 1, max, first invalid, type(uint256).max), captures a non-local contract (constructor invariants, checked/unchecked semantics, round-trip relationships, ordering guarantees), documents a user-visible revert with non-trivial control flow, prevents a known regression, or serves as executable documentation for a tricky public semantic.
Never write tests that re-implement the function under test, merely prove the language works as documented, or duplicate coverage already provided by stronger invariants.
For risk-bearing changes (business logic, protocol logic, state transitions, parsers, authorization, money-like values, security-sensitive code), favor test-first — but the test must meet a criterion above, not exist because the code is risky.
This rule decides whether a test is worth writing; the Test Integrity section below governs how every warranted test is written and maintained.

## Test Integrity
AI Coding Rules #4 decides whether a test is worth writing; these rules govern how any test that passes that bar is written and maintained. They target reward hacking: optimizing for the observable signal of success (green suite, passing CI) instead of the correctness it is supposed to measure. The list stays short deliberately — instruction compliance degrades as rule count grows — so an addition here must displace something weaker.

- **Red before green.** Write the test before the implementation, run it, and confirm it fails for the intended reason before writing code to make it pass. A test never observed failing proves nothing; claiming it "would fail" without executing it is fabricated verification. A test added to existing behavior (regression pin, executable documentation) must still be shown able to fail: temporarily break the code under test and watch it go red.
- **Never mock the system under test.** Exercise real code through the module's public boundary; prefer boundary/integration tests over unit tests wired to internals, since they are harder to game with test doubles. Mock only what is genuinely external, non-deterministic, or unavailable (third-party services, clocks, network). A test asserting against its own mock's return values verifies the mock, not the code.
- **Cover the failure paths that exist.** For every non-trivial change, check four scenario classes — success, validation failure, authorization denial, missing/not-found state — and cover each one that applies to the change. Skipping an applicable class needs a stated reason; Rule #4's information criterion still gates each individual test.
- **A failing test signals a defect, never an obstacle.** Never skip, delete, or weaken a test or its assertions to make the suite pass. Fix the root cause. If the test itself is wrong, say so explicitly and change it as its own justified edit, not as a side effect of getting to green.
- **Trivially-satisfied assertions are failures.** A test that would still pass with the implementation broken, or that passes on empty/null data, asserts nothing. The mutation check: name the change to the code under test that would make this test fail; if none exists, the test is fake and must not be committed.
- **Enforcement surfaces are read-only.** Never modify CI configuration, pre-commit hooks, lint or coverage thresholds, or any script that grades the work in order to make a check pass. Such changes require explicit human approval in the conversation; a gate the agent can edit is not a gate.
- **Conflicts halt.** If these rules collide with project guidance or a skill workflow, the conflict is a bug in the rules: stop and ask rather than silently picking a side.
